# J-me - Design Spec v0

Status: draft, 2026-11-09. Decisions marked **RULED** came from the maintainer; everything else is a
recommendation open to change.

## 1. What it is

J-me is a live-conversation producer. It listens, transcribes, and keeps a short queue of
pre-staged web searches and AI prompts that match what is being talked about right now.
The queue decays as the conversation moves on. Anything still in it is ready at the drop
of a hat: tap it and the answer, article, clip or definition is already there.

The reference image is Jamie on the Joe Rogan show: nobody asks him to prepare, but when
someone says "pull that up," it is up in seconds.

## 2. Decisions

| # | Decision | Status |
|---|----------|--------|
| 1 | Own repository, no relation to any other project | **RULED** |
| 2 | Local-first: audio, transcript, topic model and prompt generation never leave the device | **RULED** |
| 3 | End-user tool: installable, no server to stand up, usable by someone who is not a developer | **RULED** |
| 4 | Runs on any device: laptop, desktop, phone, tablet | **RULED** |
| 5 | Private by default: the queue shows on the operator's own screen; a shared display is an opt-in later | proposed |
| 6 | Automatic staging, manual pulling: J-me prepares silently and never interrupts; the human decides what to pull up | proposed |
| 7 | Two inputs: room microphone (in-person) and system audio (podcasts, video, calls) | proposed |
| 8 | Only searches leave the device, only for items that cross the staging threshold, through a provider the user picks | proposed |
| 9 | No commands, ever, for the end user. The whole thing is a toggle switch: flip it on over whatever media is chosen and the queue appears. The engine is a plug-in that consumes conversational input, not an app the user operates | **RULED** (2026-11-09) |

## 3. The core loop

```
 audio --> VAD --> streaming STT --> rolling transcript
                                         |
                                         v
                             topic tracker (embeddings over a sliding window)
                                         |
                                         v
                      anticipator (small local LLM): "what would someone
                      want pulled up right now?" -> candidate items
                                         |
                                         v
                      queue: score, dedupe, stage (prefetch top N), decay
                                         |
                                         v
                      surface: queue UI, tap to pull up, pin to keep
```

Each stage is a replaceable module behind a small interface, so a phone can run smaller
models than a desktop without the rest of the code caring.

## 4. Queue items

```
QueueItem
  id            stable hash of normalized text
  kind          search | prompt | lookup | media
                search = web query to run
                prompt = question for the local LLM over the transcript so far
                lookup = a specific entity (person, paper, product, place)
                media  = a clip, image or timestamp someone referenced
  text          the query or prompt as it would be run
  why           one line: the transcript moment that spawned it
  anchor        transcript span [t0, t1] and its topic embedding
  score         0..1, recomputed every tick (see section 5)
  state         candidate -> staged -> ready -> (expired | pinned | pulled)
  results       prefetched results, summaries, cached pages (ready state only)
  touched       last time the topic recurred in the transcript
```

States:

- **candidate**: generated by the anticipator, not yet worth a network call.
- **staged**: above the staging threshold; a fetch is in flight.
- **ready**: results cached locally; tapping shows them instantly.
- **pinned**: exempt from decay; the human wants it kept.
- **pulled**: it was shown; kept in the session log with its results.
- **expired**: fell below the floor; removed from the live queue, kept in the session log.

## 5. Decay

The queue is a priority list, not a FIFO. Every tick (about once a second):

```
age      = now - touched
recency  = exp(-age / tau)
topical  = similarity(recent window, item.anchor)      # v0: term overlap; later: embeddings
weight   = 0.5 + 0.5 * confidence
score    = (w_r * recency + w_t * topical) * weight
```

- `tau` defaults to about 90 s for live conversation and about 4 min in media mode
  (a podcast dwells on a topic longer than a dinner table does).
- `touched` resets when the topic recurs, so a subject the room keeps coming back to
  stays near the top without ever being pinned.
- `confidence` is the anticipator's own estimate; it scales the whole score so a weak
  guess starts lower and leaves sooner.
- **Staging** (spending a fetch) needs two things: score at or above `stageAt` (0.5), and
  either confidence at or above `stageConf` (0.8) or a recurrence (the room came back to
  the topic after the item was born). The first backtest (2026-11-09) showed why: with a
  score-only gate every item staged at birth, because a fresh item's recency is 1.
- Items below the **floor** (0.2) expire. Cap the live queue (default 12); lowest score
  falls off first. All of these are user-tunable.

The decay rule is the product. It needs real conversations to tune, which is why the
first slice (section 9) instruments it.

## 6. Architecture

**One codebase, two layers.**

- **UI layer**: a web front end (TypeScript). Runs inside whatever shell the device has.
  Queue column, transcript strip, pull-up panel, pin, settings.
- **Engine layer**: the core loop of section 3. Audio capture, VAD, STT, embeddings, the
  anticipator LLM, the queue, the search providers, the session log. Runs on the device.

**Delivery in two phases:**

- **Phase A (prototype, this laptop):** engine as a local Node process; UI served to
  the browser on the same machine and to any phone or tablet on the same Wi-Fi.
  This proves the loop and tunes the decay rule. It is not the end-user shape.
- **Phase B (product):** package with **Tauri v2**, which builds Windows, macOS, Linux,
  iOS and Android from the same web UI plus a Rust engine. Models run on-device. A phone
  that is too weak for the full engine can **pair to a hub** (the user's own laptop on the
  same network) and act as microphone and screen. Rust is not installed on the dev
  laptop yet; it is a Phase B prerequisite, not a Phase A one.

Why not a pure browser app: a PWA cannot capture system audio reliably, cannot keep
listening in the background on phones, and cannot run searches cross-origin without a
helper. Why not Electron: no mobile story. Tauri v2 is the one toolchain that reaches
every device the maintainer named with local compute.

## 7. Models and providers (all local, all swappable)

| Job | Desktop default | Phone default | Notes |
|-----|-----------------|---------------|-------|
| VAD | Silero VAD | Silero VAD | tiny, same everywhere |
| STT | whisper.cpp large-v3-turbo | whisper.cpp small, or Moonshine | streaming via VAD-cut chunks; Moonshine was built for on-device streaming |
| Embeddings | bge-small or nomic-embed | same | topic tracking only, 384-d is plenty |
| Anticipator | Qwen2.5 7B or Gemma 3 4B instruct, GGUF via llama.cpp | Qwen2.5 1.5B to 3B | structured JSON out: list of candidate items |
| Summarizer | same model | same | turns fetched pages into the pull-up card |
| Search | DuckDuckGo (no key) by default; Brave Search API or a self-hosted SearXNG by choice | same | the only network egress |

Phase A on this laptop can use Ollama for the LLM and a whisper.cpp or faster-whisper
binary for STT to get moving fast. Phase B swaps in llama.cpp and whisper.cpp bindings
inside the app bundle.

## 8. UI (first pass)

- **Queue column:** cards sorted by score. Opacity follows score, so decay is visible
  without a number. Ready cards show a small dot. Pinned cards sit at the top.
- **Pull-up panel:** tap a card, it opens with the cached results: top links, a
  three-line summary, the transcript moment that spawned it.
- **Transcript strip:** the last minute of text, scrolling. Tap a phrase to force a card.
- **Mode switch:** Room / Media. Changes the input source and the decay constant.
- **Ask bar:** type or say a question; it jumps the queue as a pinned prompt.
- Everything works at phone width first.

## 9. First slice: prove the loop

Build in Phase A shape, on this laptop, in TypeScript:

1. Mic -> VAD -> STT -> rolling transcript on screen. Target: words appear within 2 s.
2. Anticipator produces candidate items from the last 60 s every 10 s or on each
   finished utterance. Target: a sensible query within 5 s of the sentence that earned it.
3. Queue with the section 5 decay rule, visible in the UI with fading cards. Every score
   tick logged to a session file so the rule can be tuned from real talk.
4. DuckDuckGo prefetch for staged items; summary card on tap.
5. Media mode via system-audio loopback on Windows (WASAPI loopback).

Done means: play a 20-minute podcast, watch the queue, and find that at least half the
things you would have wanted pulled up were already ready. That is a judgment call, so
the session log records what was ready and what was pulled, to make it a number later.

## 9a. Two sides of the same tool (added 2026-11-09)

The maintainer's reframe: J-me is a tool for the people talking **and** for the people watching.

- **Podcaster / lecturer side.** Run J-me on the live show or on the finished recording.
  Review the buffer map (approve, drop, retitle). Publish the result as a **companion**.
- **Viewer / student side.** Open the companion next to the episode. It syncs to the
  player clock (YouTube embed) or to a manual clock, and shows what is live right now:
  links for each item, and a **prompt that carries the moment** (title, timestamp, the
  excerpt that earned it) ready to hand to whatever model or service the viewer uses.
  Handoff is a prefilled URL (ChatGPT, Claude, Perplexity) or copy-to-clipboard. The
  viewer needs no model, no install, no compute.

The companion is a portable JSON (`jme-companion/1`) plus one self-contained HTML page.
The backtest is therefore the production path for recorded episodes, and map quality plus
the host's review pass come before live room mode in priority. Live shows stream the
same queue to viewers over a socket; viewers on another device can sync by listening
(the local ear) later.

## 9b. The switch (ruled 2026-11-09)

The maintainer's ruling: no end user is going to run commands. The product is a toggle switch on
whatever media is chosen. What that means for each shape:

- **Phase A, now.** One launcher (`J-me.cmd`) starts the engine and opens the page; the
  page has one switch and a source choice (media / room / speakers and mic). Flipping it
  on asks the browser which tab, window or screen to listen to. **Float** pops the whole
  page into a small always-on-top window (Document Picture-in-Picture, Chrome/Edge) that
  sits over the video or any other app; closing it docks the page back. The maintainer's bar
  (2026-11-09): "it means nothing if J-me is not visible as an overlay on the video or
  audio stream." The ear should be "tied to speaker output and mic input": the
  speakers-and-mic source does that in the browser today (entire screen + system audio,
  mixed with the mic); the desktop app does it without a picker.
- **Browser extension (built 2026-11-09, `extension/`).** The switch lives in the
  toolbar; on means "this tab." The service worker takes a tab-capture stream id, an
  offscreen page turns it into 16 kHz PCM for the engine's socket (and plays it back so
  the tab stays audible), and an injected overlay draws the queue on the page itself,
  draggable, following the player into fullscreen. No page to open, nothing to pick.
- **Everything in the extension (ruled and built 2026-11-10, `extension/src/`).** Asked
  for the most accessible version, the maintainer ruled "lets try 2 with 1 and 3 as backup": 2 =
  the extension does everything itself, 1 = a hosted page (breaks the local rule), 3 =
  the tray installer. So the offscreen page now runs the ear (Silero VAD + Moonshine via
  onnxruntime-web and transformers.js, WebGPU or wasm), the same engine core, and a brain
  chosen in order: Ollama on the machine, the browser's built-in model (Prompt API), or
  WebLLM Qwen 2.5 3B. Nothing to install but the extension. Known costs: the in-browser
  brain is 30 to 45 s per call on an integrated GPU; WebLLM and an ORT WebGPU session
  cannot share the adapter, so speech runs on wasm when WebLLM is the brain; the search
  engine's HTML page refuses extension requests, so browser lookups use Wikipedia and the
  DuckDuckGo Instant Answer API. The Node engine remains the bigger-brain path.
- **Three asks from the first hand test (built 2026-11-11, v0.3.0).** The maintainer, after the
  extension ran in his Chrome: "could it bring up ai inquiry prompts? so you hit the
  prompt link and it asks your ai"; "a microphone toggle for zoom calls. so you could
  fact check yourself"; "along with internet searches it should have an image search. so
  it shows like a stream of images based on the conversation." Built as: (1) prompt
  items are no longer gated to near-certainty; a prompt must read as a question, one per
  brain call, and every card carries an "Ask <AI>" link (ChatGPT, Claude or Perplexity,
  chosen on the settings page) that opens the item with the anchoring moment as context;
  prompt cards lead with it, and only a fast brain (Ollama) also answers them locally.
  (2) Pictures: `ImageResult` on items, fetched at stage time with the links (Wikimedia
  Commons search plus the Wikipedia card's lead image), shown as a strip across the top
  of the panel, newest item first, each linking to its page. (3) The microphone: a side
  panel (`panel.html`) with a Microphone switch; the toolbar icon stays "this tab" (one
  source at a time). Echo cancellation is off on purpose so a desktop Zoom call's far end,
  coming out of the speakers, is heard too. The permission is granted once on the
  settings page because an offscreen document cannot ask. Room mode (tau 90) for the mic.
  Tested on the laptop's real microphone with the demo played through the speakers: cards
  and a picture reached the side panel; transcription through air is rougher than tab
  capture, as expected.
- **Desktop app (Phase B, Tauri).** The switch lives in the tray; on means "everything
  playing on this machine" through system-audio loopback, so any player or meeting app
  works without a browser. The engine installs once with the app and starts with it.
- **Phone.** The app's own switch, with the mic as the ear; media comes through pairing
  to the hub (section 6).
- **Announced as planned (the maintainer's Skool post, 2026-11-11), not built:** musical note and
  lyric inference (hear a song or a hummed line, pull up the track and lyrics); video cue
  (the "media" item kind made real: a referenced clip, scene or timestamp pulled up, not
  just named); and an internal RAG for inter-organizational meetings (the Node engine's
  `--docs DIR` BM25 search over a folder, grown into the extension and into shared,
  per-meeting document sets). Each is a feature request thread first; nothing here is
  promised with a date. The maintainer's framing in the post: students, lecturers, podcasters,
  journalists, interviewers, anyone who wants to fact-check instantly and fairly, both the
  content and themselves.
- **Video cue, built 2026-11-11 (v0.4.0), the maintainer: "lets start there".** A second strip
  under the pictures: videos fetched with each card's results (`VideoResult`, YouTube's
  results page parsed for its `videoRenderer` entries, keyless; the extension holds the
  youtube.com host permission for it). In the side panel a click plays the video in an
  embedded player at the top; on a page it opens YouTube. The "media" item kind is now
  real: the anticipator is told to name a specific video, clip, scene, talk or
  performance, and the gate dropped from 0.8 to 0.6. Not built: finding the exact scene
  inside a video (no open API does that).
- **Answers inside the card (v0.5.0, 2026-11-11).** The maintainer: "can the prompts be piped into
  the plugin without replacing the tab of the video?" Two answers. The hand-off link now
  opens the AI in a small popup window beside the video (the service worker opens it; the
  listened-to tab keeps focus). And `extension/src/frontier.ts`: with the user's own key
  (OpenAI, Anthropic, or any OpenAI-compatible server such as Ollama with no key), every
  card gets "Answer here" and the answer lands in the card through `engine.setAnswer`.
  The key lives in chrome.storage.local; only the question and the anchoring moment go
  out, only on the press. This is the "frontier on demand" rung of the model ladder made
  concrete. Also 0.4.1: the page's title, author and description become brain context;
  0.4.2: the star toggles off again.
- **The bridge and the MCP server (v0.6.0, 2026-11-11).** The maintainer: "is there a way agents
  can use J-me to streamline automations?" then "lets build the bridge and the mcp... agent
  friendly". `engine/src/bridge.ts`: a local HTTP process the extension feeds every event
  (setting "share with a local agent"), holding the live cards, the pinned ones and the last
  hour of transcript; `/state`, `/events` (SSE), `/command` (ask, pin, unpin, pause, resume)
  and the extension's long-poll `/commands`. `engine/src/mcp.ts`: an MCP server over stdio
  on top (starts the bridge itself when the port is free): jme_state, jme_cards,
  jme_transcript, jme_ask, jme_pin, jme_unpin, jme_pause, jme_resume, jme_wait. Agent asks
  are labelled "asked by <agent>" and capped at six a minute; the pause button stays the
  human's override. Also 0.5.1 pause/resume with catch-up, 0.5.2 side-panel detection.
- **The calculator (v0.7.0, 2026-11-12).** The maintainer: "any time a figure, calculation, ratio,
  stat... the figure would be put into a calculator and would flag it as an inaccuracy...
  25% x and 50% y and 50% z... an inherent fallacy", and figures get priority as searches.
  `engine/src/numbers.ts`, deterministic, no model: number words to digits; four checks
  (parts of a whole past 100%, excluding "N% of <different whole>"; from-A-to-B against a
  stated % change; "A out of B" against a stated %; doubled/tripled/halved/"N times"
  against a from-to). A hit becomes a `math` card at once (confidence 1, answer = the
  arithmetic, red edge, no fetch). Figures: the brain is told a spoken figure is a priority,
  and any non-prompt candidate carrying a figure stages at confidence 0.85. Conservative on
  purpose: a false flag costs trust.
- **The documents, step 1 (v0.8.0, 2026-11-13).** The maintainer: "ok lets start on the RAG". The
  Node engine's folder search became a platform-free `DocIndex` (BM25 over paragraphs,
  with a relevance floor so a single weak term is not a hit); the settings page reads a
  chosen folder once (File System Access API, a click) and stores the text in IndexedDB;
  the offscreen page builds the index from the store, so it needs no folder handle and no
  gesture; the engine searches it first for every card, and lists the document names in
  the brain's context so it proposes lookups in their terms. Hits render as a green block
  with the paragraph. Steps 2 to 4 (embeddings, meeting sets, inter-organizational) remain
  in `docs/NEXT.md`; inter-organizational stays last and starts with a conversation.

The engine stays the same under all four: a text-in / events-out plug-in (section 9a; the
segment door and its `docs/API.md` are the next build), with the audio ear as one optional
source.

## 10. Non-goals for v0

Accounts, cloud sync, speaker diarization, multi-language, a shared/cast display,
meeting-notes export, and any integration with other projects. Each is a later decision.

## 11. Open questions

1. Phase A stack: Node + TypeScript engine (Node 24 is installed) versus a Python engine
   for the prototype. Recommendation: TypeScript, because the UI is TypeScript either way
   and Phase B carries the UI across unchanged.
2. Wake phrase ("J-me, pull that up") in v0, or tap only? Recommendation: tap only in
   v0; the wake phrase is a later add once STT latency is known.
3. How much to prefetch: result list only, or fetch and summarize the top page too?
   Costs bandwidth and reveals more to the network. Recommendation: result list by
   default, page fetch on tap, a setting to prefetch pages.
4. Name: "J-me" as the product name, or working title. Pending the competitive and
   naming check (docs/COMPETITIVE_LANDSCAPE.md once written).
